01会員フロー

起点はログイン画面。仮パスワードで入った場合だけ、ホームの手前に強制変更が挟まります。 記録とマイページは 9/20版では封印し、タブは押せない状態で見せます。 全画面スマートフォンの縦長 1画面に収める前提で、ホーム以降は画面下部のタブバーで行き来します。

02管理者フロー

ダッシュボードが7機能へのハブになります。会員に対する操作(記録の代理入力・パスワード操作)は、 会員一覧から会員を選んだ「会員詳細」を経由する形に揃えました。 こちらは店舗のタブレット / PC で使う想定のため、一覧や集計は横幅を使ったレイアウトにします。

03予約可否の判定(M-04 の中身)

3つの課金形態で分岐するのは A の契約チェックだけで、B の枠チェックは全形態共通です。 画面としては1つですが、押せる / 押せないの理由がここで決まるため、エラー文言の設計にそのまま効きます。

05決めていただきたいこと

画面の詳細設計に入る前に固めておきたい5点です。いずれも「こちらの案で進めてよいか」の確認です。

  1. 新規採番した5画面のIDを確定してよいか

    M-10 体験予約フォーム / A-03d 会員詳細 / A-09 メニュー設定 / A-10 予約枠カレンダー / A-11 トレーナー紐づけ。いずれも 9/20版のスコープにあるのに設計書で画面IDが振られていなかったものです。

  2. 予約完了(M-05)からアンケート(M-06)への導線は毎回出すか

    基本設計書は「アンケートは予約完了後導線」とだけ書かれています。毎回出すと煩わしいので、初回のみ / 任意のバナー表示、あたりが現実的です。

  3. 管理者代行リセット(A-08)を実行できるロール

    パスワード再設定追補で「店舗管理者は可、スタッフは不可 等、運用に合わせて設定」として保留になったままの項目です。店舗管理者のみを既定にする想定です。

  4. 予約(M-04)の順序は「メニュー → 日時」か「日時 → メニュー」か

    予約枠は全メニュー共通なので、どちらの順でも作れます。保有している権利(通い放題・回数券)から入るほうが会員には分かりやすいと考えており、メニュー先行を想定しています。

  5. 体験予約フォーム(M-10)の入口

    公式サイトやSNSからの外部リンクで直接開く想定です。アプリ内のログイン画面にも導線を置くかどうかをご判断ください。

  6. 会員側を「アプリ」としてどこまで仕上げるか

    ホーム画面にアイコンを置いてアプリのように全画面で起動する形(PWA)は 9/20版に含められます。App Store / Google Play で配信するネイティブアプリは、審査・開発者登録・実装方式の変更が必要でリリース日に間に合わないため、Phase2 での対応を想定しています。どちらを指しているかのご確認をお願いします。
